# 📋 文档组织方案

## 概述

项目文档遵循**渐进式披露（Progressive Disclosure）**原则，分层组织以满足不同用户的需求。

## 设计原则

### 1. 渐进式披露

文档按**学习路径**而不是**字母顺序**组织：

```
入门 → 体验 → 学习 → 参考 → 深入 → 存档
```

- **入门层**：README、QUICK_START（快速回答"是什么"）
- **体验层**：示例和教程（快速回答"怎么做"）
- **学习层**：API、ARCHITECTURE（深入回答"如何工作"）
- **参考层**：完整文档（查询特定功能）
- **深入层**：设计文档（理解权衡和决策）
- **存档层**：历史报告（项目记录）

### 2. 关注点分离

文档按**关注点**而不是**时间**分类：

| 文档类型 | 关注点 | 位置 | 受众 |
|---------|--------|------|------|
| **入门指南** | 快速上手 | 根目录 | 所有人 |
| **技术指南** | 深入学习 | 根目录 | 开发者 |
| **发布指南** | 版本管理 | `guides/` | 维护者 |
| **完成报告** | 历史记录 | `reports/` | 项目管理 |
| **使用示例** | 实际案例 | `examples/` | 所有人 |

### 3. 懒加载思维

不强制用户阅读所有文档：

- 新用户只需阅读 README + QUICK_START
- 开发者需要时再查看 ARCHITECTURE + API
- 维护者定期查看 reports/ 了解项目历史

## 文件结构详解

### 根目录文档

#### 📖 快速入门
- **README.md** — 项目介绍、功能、安装、性能
- **QUICK_START.md** — 5分钟快速体验

#### 🔨 开发相关
- **ARCHITECTURE.md** — 系统架构和模块设计
- **DEVELOPMENT.md** — 开发工作流、测试、规范
- **API.md** — 完整的 API 文档和示例

#### 🎯 项目管理
- **ROADMAP.md** — 功能规划和里程碑
- **ACCEPTANCE_CHECKLIST.md** — 验收标准和竞品对标

#### 📊 性能参考
- **PERFORMANCE_REPORT.md** — 基准测试结果

### guides/ — 发布指南

仅包含与**版本发布和用户通讯**相关的文档：

- **CHANGELOG_0.2.0.md** — 版本变更日志
- **RELEASE_GUIDE.md** — 发布流程和清单
- **ANNOUNCEMENT.md** — 版本发布公告

**维护策略**：每个主要版本保留一份。

### reports/ — 开发报告

保存所有的**完成报告、计划文档和开发总结**：

- **PHASE*.md** — 各开发阶段的完成报告
- **ACCEPTANCE_*.md** — 验收报告
- **COMPLETION_*.md** — 完成度报告
- **CYCLE*_REPORT.md** — 开发循环总结
- ***_PLAN.md** — 开发计划文档

**维护策略**：按日期或版本保留，作为项目历史记录。

### examples/ — 使用示例

包含**可运行的示例代码和渲染结果**：

- **org_chart_simple.mmd** — Mermaid 源文件
- **org_chart_barycenter.png** — 渲染结果（展示最优布局）

**维护策略**：保留最好的示例和最新的渲染结果。

## 导航流程

### 新用户流程
```
README.md
    ↓
是否满足需求？
    ↓─── 是 ──→ QUICK_START.md
    ↓
否，需要更多信息
    ↓
API.md / ARCHITECTURE.md
```

### 开发者流程
```
QUICK_START.md（设置环境）
    ↓
ARCHITECTURE.md（理解设计）
    ↓
DEVELOPMENT.md（开发工作流）
    ↓
ROADMAP.md（选择任务）
    ↓
开始编码
```

### 维护者流程
```
ROADMAP.md（规划）
    ↓
开发循环
    ↓
reports/（保存完成报告）
    ↓
guides/ANNOUNCEMENT.md（发布公告）
    ↓
CHANGELOG_X.md（更新变更日志）
```

## 为什么这样组织？

### 1. 减少认知负荷

新用户不需要找到 27 份文档，只需要 2-3 份入门文档。

### 2. 快速查找

开发者知道去哪里找：
- 快速问题 → README/QUICK_START
- API 问题 → API.md
- 架构问题 → ARCHITECTURE.md
- 历史信息 → reports/

### 3. 易于维护

- 入门文档保持简洁，避免重复
- 临时文件（中间版本、测试结果）快速清理
- 历史文档保留在 reports/ 中，不污染根目录

### 4. 支持增长

当项目增长时，新文档可以有组织地添加：
- 新的指南 → guides/
- 新的报告 → reports/
- 新的示例 → examples/

## 维护指南

### 何时添加新文档

✅ 添加到根目录：
- 广泛适用的指南（如 DEVELOPMENT.md）
- 核心参考文档（API.md、ARCHITECTURE.md）
- 项目计划（ROADMAP.md）

✅ 添加到 guides/：
- 版本相关的文档
- 发布流程文档

✅ 添加到 reports/：
- 完成报告
- 开发计划
- 研究和分析

✅ 添加到 examples/：
- 示例代码
- 渲染结果
- 教程

### 何时删除文档

❌ 删除的时机：
- 中间版本的临时文件（已做）
- 过期的计划文档（1年以上未更新）
- 冗余的文档（内容已合并）

✓ 不删除的文件：
- 历史报告（保留在 reports/）
- 已发布版本的变更日志（保留在 guides/）
- API 文档（定期更新而不是删除）

### 定期维护

每个季度检查一次：

1. **根目录** — 删除临时文件，更新索引
2. **guides/** — 确保最新版本文档完整
3. **reports/** — 按日期组织，存档过期报告
4. **examples/** — 保留最新和最好的示例
